## 1. 개요

### 1.1 한 줄 정의

매일의 건강 수치(몸무게·키·혈압·혈당)를 기록하면, 서버가 **BMI를 자동 계산하고 건강 상태를 분류**하며, 위험 항목에 **경고를 생성**하고, 쌓인 데이터로 **통계**를 제공하는 REST API.

### 1.2 해결하려는 문제

건강검진 수치를 받아도 "이 숫자가 정상인지" 비전문가는 판단하기 어렵다. 측정값을 입력하는 순간 분류·경고가 함께 나와야 의미가 생긴다. 이 API는 **원본 저장과 해석을 한 번의 요청으로** 끝낸다.

### 1.3 목표 사용자

- 자신의 건강 수치를 꾸준히 기록하려는 개인
- 수치의 정상/위험 여부를 즉시 확인하고 싶은 비전문가

### 1.4 범위

**포함**

- 회원가입 · 로그인 (JWT 인증)
- 건강 기록 CRUD (본인 기록으로 접근 제한)
- BMI · 혈압 · 공복혈당 자동 분류 및 경고 생성
- 기간 검색, 평균 통계
- 모바일 우선 웹 화면
- Docker 실행 및 데이터 영속성

**제외 (향후 과제)**

- Alembic 마이그레이션
- HTTPS · 클라우드 배포
- 리프레시 토큰 · 토큰 무효화
- 추세 그래프, 알림 발송

### 1.5 학습 목표 (과제 관점)

FastAPI로 REST API 설계, Pydantic 검증, 조건 분기 로직, 인증, 데이터 영속성, Docker 실행까지 하나의 흐름으로 경험한다. 건강 분류 기준은 학습용으로 단순화한 값이며 의학적 진단이 아니다.

## 2. 핵심 동작 흐름

```
회원가입 · 로그인 → 토큰 발급
        │
        ▼
사용자가 건강 수치를 POST로 전송 (토큰 첨부)
        │
        ▼
서버가 저장 + BMI 계산 + 혈압/혈당 분류 + 경고 생성
        │
        ▼
GET으로 기록 · 검색 · 통계를 JSON으로 응답 (본인 것만)
        │
        ▼
Docker 컨테이너로 실행 (/docs 또는 웹 화면에서 사용)
```

## 5. 분류 기준

### 5.1 BMI

`BMI = 몸무게(kg) ÷ (키(m) × 키(m))` — 키가 cm이면 100으로 나눠 m로 변환.

| 구간 | 분류 |
|---|---|
| 18.5 미만 | 저체중 |
| 18.5 ~ 22.9 | 정상 |
| 23 ~ 24.9 | 과체중 |
| 25 이상 | 비만 |

### 5.2 혈압

| 조건 | 분류 |
|---|---|
| 수축기 < 120 **그리고** 이완기 < 80 | 정상 |
| 120~139 **또는** 80~89 | 주의 |
| 수축기 ≥ 140 **또는** 이완기 ≥ 90 | 고혈압 |

> 구현 시 고혈압 → 정상 → 주의 순으로 검사한다. 정상을 먼저 판정하면 한쪽만 높은 값이 잘못 분류된다.

### 5.3 공복혈당

| 구간 | 분류 |
|---|---|
| 100 미만 | 정상 |
| 100 ~ 125 | 공복혈당장애 |
| 126 이상 | 당뇨 의심 |

### 5.4 경고 (warnings) 규칙

- 체중이 저체중 또는 비만이면 경고 추가
- 혈압이 정상이 아니면 경고 추가
- 혈당이 정상이 아니면 경고 추가
- 경고가 하나라도 있으면 마지막에 전문가 진료 권고를 덧붙임
- 해당 없으면 빈 목록 `[]`

## 6. 통계

`GET /me/stats` — 로그인한 사용자의 전체 기록을 집계한다.

| 항목 | 설명 |
|---|---|
| `count` | 총 기록 수 |
| `avg_weight` | 평균 몸무게 |
| `avg_bmi` | 평균 BMI |
| `avg_systolic` / `avg_diastolic` | 평균 혈압 |
| `avg_blood_sugar` | 평균 공복혈당 |

**기록이 0건일 때** — `count`는 0, 나머지 평균은 `null`. 오류를 내지 않는다(0으로 나누기 방지).

**avg_bmi 계산 방식** — BMI는 저장값이 아니므로, 기록마다 `calc_bmi`로 다시 계산한 뒤 평균을 낸다.

## 7. 인증 요구사항

### 7.1 흐름

```
회원가입 → 비밀번호를 bcrypt 해시로 변환해 저장 (원문 저장 안 함)
   │
로그인 → 이메일/비밀번호 확인 → JWT 토큰 발급 (유효기간 24시간)
   │
이후 요청 → 헤더에 Authorization: Bearer <토큰>
   │
서버 → 토큰을 해석해 사용자 식별 → 본인 기록만 접근
```

### 7.2 요구사항

| 항목 | 규칙 |
|---|---|
| 비밀번호 저장 | bcrypt 해시. 원문은 어디에도 저장하지 않는다 |
| 비밀번호 길이 | 8자 이상 72자 이하 |
| 토큰 유효기간 | 24시간 |
| 토큰 전달 | HTTP 헤더 `Authorization: Bearer <토큰>` |
| 기록 접근 | 본인 기록만. 타인의 기록은 404로 응답 |
| 로그인 실패 | 원인을 구분하지 않고 동일한 401 반환 |
| 로그아웃 | 클라이언트가 토큰을 삭제. 서버 API 없음 |
| 응답 노출 | `password_hash`는 어떤 응답에도 포함되지 않는다 |

### 7.3 화면 요구사항

- 접속 시 토큰이 있고 유효하면 앱 화면, 아니면 로그인 화면
- 회원가입 성공 시 자동으로 로그인까지 진행
- 401 응답을 받으면 자동 로그아웃 후 로그인 화면으로 이동
- 새로고침해도 로그인 상태가 유지된다

## 8. 응답 코드 정책

| 코드 | 상황 |
|---|---|
| 200 | 모든 성공 응답 (생성 · 삭제 포함, 일관성 위해 통일) |
| 400 | 논리적으로 잘못된 요청 (시작일 > 종료일) |
| 401 | 인증 실패 (토큰 없음 · 만료 · 위조, 로그인 정보 불일치) |
| 404 | 대상 없음 (존재하지 않거나 내 것이 아닌 기록) |
| 409 | 중복 충돌 (이메일 중복, 같은 날짜 기록 중복) |
| 422 | 값 검증 실패 (미래 날짜, 수축기 ≤ 이완기, 범위 초과) |

| 필드 | 규칙 | 위반 시 |

| 필드 | 규칙 | 위반 시 |
|---|---|---|
| `start` | 필수 · 종료일보다 늦을 수 없음 | 422 / 400 |

### 9.4 2단계 방어

| 위치 | 역할 |
|---|---|

브라우저 쪽은 편의 장치이고, 최종 방어선은 서버다.

## 11. 주요 설계 결정

기능 명세를 넘어, 구현 과정에서 내린 판단과 근거를 정리한다.

### 11.1 저장 방식 — JSON 파일 대신 PostgreSQL

과제 명세는 JSON 파일 저장을 제시했으나, 요구사항의 핵심인 **"서버를 재시작해도 데이터가 유지될 것"** 을 볼륨 기반 PostgreSQL로 구현했다.

- **동시 쓰기 안전성** — JSON 파일은 요청이 겹치면 내용이 깨질 수 있다.
- **제약 조건을 DB가 보장** — 외래 키와 복합 유니크를 애플리케이션 코드가 아닌 DB 레벨에서 지킨다.
- **검색 · 집계** — 기간 검색과 평균 계산을 인덱스 기반으로 처리한다.

### 11.2 계산 값을 저장하지 않는다

`bmi`, 분류 3종, `warnings`는 DB에 저장하지 않고 응답을 만들 때마다 계산한다.

분류 기준은 가이드라인 개정으로 바뀔 수 있다. 계산 결과를 저장해두면 기준이 바뀌는 순간 과거 데이터 전체가 잘못된 값이 된다.

### 11.3 성공 응답을 200으로 통일

REST 관례상 생성은 201, 삭제는 204를 쓰지만 200으로 통일했다. 클라이언트가 성공 여부를 단일 조건으로 판단할 수 있어 처리가 단순해진다.

### 11.4 URL에서 user_id를 제거

`/users/{user_id}/logs` 대신 `/me/logs`를 쓴다. 클라이언트가 남의 id를 지정할 방법 자체가 사라진다.

### 11.5 남의 기록에 403이 아닌 404

403("권한 없음")은 *"그 id의 기록이 존재하긴 한다"* 는 사실을 알려주는 셈이다. id를 훑어 타인의 기록 수를 파악할 수 있으므로, 없는 것과 남의 것을 구분하지 않는다.

### 11.6 분류 로직을 별도 파일로 분리

`health_rules.py`는 DB·프레임워크와 무관한 순수 함수만 담는다. 기준이 바뀌어도 라우트와 스키마는 건드리지 않는다.

### 순서에 대한 판단

**사용자 모델을 분류 로직보다 먼저 넣었다.** 테이블에 컬럼을 추가하면 기존 데이터와 구조가 어긋난다. 실제 데이터가 쌓이기 전에 스키마를 확정해야 재작업 비용이 없다.

**화면을 인증보다 먼저 만들었다가 다시 손봤다.** 인증을 붙이면서 엔드포인트가 `/me` 계열로 바뀌어 프론트엔드를 한 번 더 수정해야 했다. 인증을 먼저 넣었다면 화면 작업이 한 번으로 끝났을 것이다.
