## 1. 프로젝트 개요

### 1.1 배경

개인의 건강 상태(체중, 혈압, 공복혈당 등)는 하루 단위로 기록해두었을 때 비로소 추세를 파악할 수 있다. 그러나 측정값 자체는 숫자에 불과해, 비전문가가 "이 수치가 정상인지" 판단하기 어렵다.

### 1.2 목적

일일 건강 측정값을 저장·조회하는 REST API를 구현하고, 저장된 원본 데이터를 바탕으로 **서버가 자동으로 건강 상태를 분류·경고**하여 사용자가 수치의 의미를 즉시 이해할 수 있도록 한다.

### 1.3 범위

**포함 (구현 완료)**

- 회원가입 · 로그인 (JWT 토큰 인증)
- 본인 기록으로 접근이 제한되는 건강 기록 CRUD
- BMI / 혈압 / 공복혈당 자동 분류 및 경고 생성
- 기간별 기록 조회 · 날짜 범위 검색 · 평균 통계
- 모바일 우선 웹 화면
- Docker 기반 실행 환경 및 데이터 영속성

**제외 (향후 과제)**

- Alembic 마이그레이션
- HTTPS 적용 및 클라우드 배포
- 리프레시 토큰 · 토큰 무효화
- 추세 그래프, 알림 발송

## 2. 기술 스택 및 선정 사유

| 영역 | 기술 | 선정 사유 |
|---|---|---|
| 웹 프레임워크 | FastAPI | 타입 힌트 기반 자동 검증, Swagger 문서 자동 생성 |
| ORM | SQLAlchemy 2.0 | 파이썬 코드로 DB 조작, 표준적이고 자료가 풍부 |
| 데이터 검증 | Pydantic v2 | 요청 검증과 응답 직렬화를 한 곳에서 처리 |
| 데이터베이스 | PostgreSQL 16 | 제약 조건(FK, Unique) 지원이 견고함 |
| 비밀번호 해시 | bcrypt | 단방향 해시로 원문 복원 불가, salt 자동 적용 |
| 토큰 | PyJWT | 서버가 세션을 보관하지 않아 구조가 단순함 |
| 실행 환경 | Docker Compose | 앱과 DB를 함께 관리, 어느 환경에서나 동일하게 실행 |
| 화면 | HTML · CSS · Vanilla JS | 별도 빌드 도구 없이 정적 파일로 서빙 |

## 3. 시스템 구성

```
[웹 화면 / Swagger UI]
            │  HTTP (포트 4923) · Authorization: Bearer <토큰>
            ▼
┌───────────────────────────┐
│  api 컨테이너              │
│  FastAPI + Uvicorn (8000) │
│  · 정적 파일(/static) 서빙 │
└───────────┬───────────────┘
            │  내부 네트워크
            ▼
┌───────────────────────────┐
│  db 컨테이너               │
│  PostgreSQL 16 (5432)     │
└───────────┬───────────────┘
            ▼
      [ pgdata 볼륨 ]  ← 컨테이너 삭제와 무관하게 데이터 보존
```

### 3.1 데이터 영속성 설계

컨테이너는 삭제 시 내부 데이터가 함께 사라진다. 이를 방지하기 위해 PostgreSQL 데이터 디렉터리를 **named volume(`pgdata`)** 에 연결한다.

| 명령 | 데이터 |
|---|---|
| `docker compose restart` | 유지됨 |
| `docker compose down` | 유지됨 |
| `docker compose down -v` | **삭제됨 (주의)** |

### 3.2 포트 설계

| 구간 | 포트 |
|---|---|
| 외부 → api 컨테이너 | 4923 |
| api 컨테이너 내부 (uvicorn) | 8000 |
| api → db (컨테이너 간 통신) | 5432 |

DB 포트는 외부에 노출하지 않고 컨테이너 내부 통신만 허용한다.

## 4. 데이터 모델

### 4.1 ERD

```
User (1) ──────< (N) HealthLog
```

사용자 한 명이 여러 건강 기록을 가진다. 사용자 삭제 시 해당 기록도 함께 삭제된다(CASCADE).

### 4.2 users 테이블

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | Integer | PK | 사용자 식별자 |
| email | String(255) | Unique, Not Null | 로그인 아이디 (중복 불가) |
| nickname | String(50) | Not Null | 표시 이름 |
| password_hash | String(255) | Not Null | bcrypt 해시 (원문 저장 안 함) |
| created_at | DateTime | 자동 | 생성 시각 |

### 4.3 health_logs 테이블

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | Integer | PK | 기록 식별자 |
| user_id | Integer | FK → users.id (CASCADE) | 작성자 |
| date | Date | Not Null | 측정일 |
| weight | Float | Not Null | 몸무게 (kg) |
| height | Float | Not Null | 키 (cm) |
| systolic | Integer | Not Null | 수축기 혈압 |
| diastolic | Integer | Not Null | 이완기 혈압 |
| blood_sugar | Integer | Not Null | 공복 혈당 (mg/dL) |
| steps | Integer | Nullable | 걸음 수 |
| sleep_hours | Float | Nullable | 수면 시간 |
| memo | String(500) | Nullable | 메모 |
| created_at | DateTime | 자동 | 생성 시각 |
| updated_at | DateTime | 자동 | 수정 시각 |

**복합 유니크 제약:** `(user_id, date)`
한 사용자가 같은 날짜에 두 개의 기록을 만들 수 없다.

### 4.4 저장하지 않는 값 (계산 필드)

`bmi`, `bmi_category`, `bp_category`, `sugar_category`, `warnings` 는 **DB에 저장하지 않고 응답 시점에 계산**한다.

> **설계 근거:** 분류 기준은 의학 가이드라인 개정에 따라 변경될 수 있다. 계산 결과를 저장해두면 기준 변경 시 과거 데이터 전체가 잘못된 값이 된다. 계산식만 관리하면 항상 최신 기준이 적용된다.

## 5. 비즈니스 로직 (분류 기준)

분류 규칙은 `app/health_rules.py` 에 분리하여, 기준 변경 시 해당 파일만 수정하면 되도록 한다.

### 5.1 BMI

`BMI = 체중(kg) ÷ (키(m))²`

| 구간 | 분류 |
|---|---|
| 18.5 미만 | 저체중 |
| 18.5 ~ 22.9 | 정상 |
| 23 ~ 24.9 | 과체중 |
| 25 이상 | 비만 |

※ 아시아-태평양 기준을 적용한다. (WHO 국제 기준은 25부터 과체중)

### 5.2 혈압

| 조건 | 분류 |
|---|---|
| 수축기 < 120 **그리고** 이완기 < 80 | 정상 |
| 120~139 **또는** 80~89 | 주의 |
| 수축기 ≥ 140 **또는** 이완기 ≥ 90 | 고혈압 |

**구현 유의사항:** 반드시 고혈압 → 정상 → 주의 순으로 검사한다. 정상을 먼저 검사하면 `수축기 150 / 이완기 70` 같은 값이 "주의"로 잘못 분류된다.

### 5.3 공복혈당

| 구간 | 분류 |
|---|---|
| 100 미만 | 정상 |
| 100 ~ 125 | 공복혈당장애 |
| 126 이상 | 당뇨 의심 |

### 5.4 경고 메시지 (warnings)

세 분류 중 정상이 아닌 항목에 대해 안내 문구를 생성한다. 경고가 하나라도 있으면 마지막에 전문가 진료 권고 문구를 덧붙인다. 해당 없으면 빈 목록 `[]`.

## 7. 인증 설계

### 7.1 흐름

```
회원가입 → 비밀번호를 bcrypt 해시로 변환해 저장 (원문 저장 안 함)
   │
로그인 → 이메일/비밀번호 확인 → JWT 토큰 발급 (유효기간 24시간)
   │
이후 요청 → 헤더에 Authorization: Bearer <토큰>
   │
서버 → 토큰을 해석해 사용자 식별 → 본인 기록만 접근
```

### 7.2 설계 결정과 근거

**세션이 아니라 토큰을 선택했다.**
세션 방식은 서버가 로그인 상태를 기억해야 해서 저장소가 필요하다. JWT는 토큰 자체에 정보가 담겨 서버가 상태를 보관하지 않아도 되므로, 단일 컨테이너 구조에 더 잘 맞는다.

**URL에서 `user_id`를 제거했다.**
`/users/{user_id}/logs` 대신 `/me/logs`를 쓴다. 클라이언트가 남의 id를 지정할 방법 자체가 사라진다.

**남의 기록에는 403이 아니라 404를 반환한다.**
403("권한 없음")은 *"그 id의 기록이 존재하긴 한다"* 는 사실을 알려주는 셈이다. id를 훑어 타인의 기록 수를 파악할 수 있으므로, 없는 것과 남의 것을 구분하지 않는다.

**로그인 실패 시 원인을 구분하지 않는다.**
"이메일이 없음"과 "비밀번호 틀림"을 나누면 가입 여부가 새어나간다. 두 경우 모두 같은 401 메시지를 반환한다.

**로그아웃 API를 두지 않았다.**
JWT는 서버가 상태를 저장하지 않으므로, 클라이언트가 토큰을 버리는 것이 곧 로그아웃이다. 화면에서는 저장된 토큰을 삭제하는 방식으로 구현했다.

## 8. 응답 코드 정책

### 8.1 성공

| 코드 | 상황 |
|---|---|
| 200 | 모든 성공 응답 |

> **설계 결정:** REST 관례상 생성은 201, 삭제는 204를 쓰지만, 본 프로젝트는 **200으로 통일**한다. 클라이언트가 성공 여부를 단일 조건으로 판단할 수 있어 처리가 단순해진다.

### 8.2 실패

| 코드 | 의미 | 발생 예시 |
|---|---|---|
| 400 | 논리적으로 잘못된 요청 | 시작일 > 종료일 |
| 401 | 인증 실패 | 토큰 없음·만료·위조, 로그인 정보 불일치 |
| 404 | 대상 없음 | 존재하지 않거나 내 것이 아닌 log_id |
| 409 | 중복 충돌 | 이메일 중복, 같은 날짜 기록 중복 |
| 422 | 값 검증 실패 | 미래 날짜, 수축기 ≤ 이완기, 범위 초과 |
| 500 | 서버 내부 오류 | 처리되지 않은 예외 (발생 시 버그) |

**400과 422의 구분:** 400은 코드에서 명시적으로 발생시키는 비즈니스 규칙 위반, 422는 Pydantic이 자동 발생시키는 형식·값 검증 실패다. 422는 어떤 필드가 왜 틀렸는지 응답에 자동 포함되어 클라이언트 처리에 유리하다.

## 9. 검증 규칙

### 9.1 건강 기록

| 대상 | 규칙 | 실패 시 |
|---|---|---|
| date | 미래 날짜 불가 | 422 |
| weight | 0 초과 500 미만 · 소수 1자리로 반올림 | 422 |
| height | 50 초과 300 미만 · 소수 1자리로 반올림 | 422 |
| systolic | 60 ~ 180 | 422 |
| diastolic | 40 ~ 120 | 422 |
| 혈압 관계 | 수축기 > 이완기 | 422 |
| blood_sugar | 40 ~ 400 | 422 |
| steps | 0 ~ 30,000 | 422 |
| sleep_hours | 0 ~ 24 · 소수 1자리로 반올림 | 422 |
| memo | 500자 이하 | 422 |
| (user_id, date) | 조합 중복 불가 | 409 |

### 9.2 사용자

| 대상 | 규칙 | 실패 시 |
|---|---|---|
| email | 이메일 형식 · 중복 불가 | 422 / 409 |
| nickname | 1 ~ 50자 | 422 |
| password | 8 ~ 72자 | 422 |

### 9.3 2단계 방어

| 위치 | 역할 |
|---|---|
| 브라우저 (`app.js`) | 범위를 벗어나는 값이 입력칸에 찍히지 않게 차단 |
| 서버 (`schemas.py`) | 실제 차단. 개발자 도구로 우회해도 여기서 걸린다 |

브라우저 쪽은 편의 장치이고, 최종 방어선은 서버다.

## 10. 디렉터리 구조

```
dyhealth-log/
├── app/
│   ├── __init__.py
│   ├── main.py            # 라우트 정의
│   ├── auth.py            # 비밀번호 해시 · 토큰 발급/검증
```

### 순서에 대한 판단

**6단계를 7단계보다 먼저 배치했다.** 테이블에 컬럼을 추가하면 기존 데이터와 구조가 어긋난다. 실제 데이터가 쌓이기 전에 스키마를 확정해야 재작업 비용이 없다.

**9단계(화면)를 11단계(인증)보다 먼저 진행한 것은 아쉬운 순서였다.** 인증을 붙이면서 엔드포인트가 `/me` 계열로 바뀌어 화면을 한 번 더 수정해야 했다. 인증을 먼저 도입했다면 화면 작업이 한 번으로 끝났을 것이다.

**14단계를 배포 전에 두었다.** 배포 후에는 볼륨 삭제로 스키마를 갱신할 수 없다. 마이그레이션 도구가 없으면 구조 변경 시 데이터를 버려야 한다.

## 12. 테스트 계획

### 12.1 인증

1. 회원가입 → id 발급, `password_hash` 미노출 확인
2. 로그인 → 토큰 발급 확인
3. 토큰 없이 보호된 API 호출 → 401
4. 이메일 중복 가입 → 409
5. 틀린 비밀번호 로그인 → 401

### 12.2 정상 흐름

1. 기록 생성 → 계산 필드 포함 응답 확인
2. 목록 조회 → 생성한 기록 확인
3. 부분 수정 → 변경 필드만 반영 확인
4. 삭제 → 재조회 시 404 확인
5. 검색 · 통계 결과 확인

### 12.3 접근 제어 (인증의 핵심)

| 케이스 | 기대 |
|---|---|
| A가 기록 생성 후 B로 로그인 → 목록 조회 | 빈 배열 |
| B가 A의 log_id로 단건 조회 | 404 |
| B가 A의 log_id로 삭제 시도 | 404 |

### 12.4 예외 처리

| 케이스 | 기대 코드 |
|---|---|
| 같은 날짜 기록 중복 | 409 |
| 시작일 > 종료일 | 400 |
| 미래 날짜 기록 | 422 |
| 수축기 ≤ 이완기 | 422 |
| 범위 초과 (수축기 190 등) | 422 |

### 12.5 경계값

분류 기준의 경계는 오류가 발생하기 쉬우므로 반드시 확인한다.

| 입력 | 기대 분류 |
|---|---|
| BMI 18.5 | 정상 |
| BMI 23.0 | 과체중 |
| BMI 25.0 | 비만 |
| 수축기 150 / 이완기 70 | 고혈압 |
| 수축기 119 / 이완기 79 | 정상 |
| 혈당 100 | 공복혈당장애 |
| 혈당 126 | 당뇨 의심 |

### 12.6 영속성 · 실행 가능성

- `docker compose down` 후 재기동하여 기존 기록이 유지되는지 확인한다.
- 새 폴더에 clone 후 `docker compose up`으로 바로 실행되는지 확인한다.

## 14. 한계 및 향후 과제

### 14.1 현재 한계

- **의학적 판단이 아니다.** 제공하는 분류는 단순화한 학습용 기준이며 진단이 아니다. 응답의 `warnings`에도 전문가 진료 권고를 포함한다.
- **토큰을 즉시 무효화할 수단이 없다.** JWT 특성상 발급된 토큰은 만료 전까지 유효하다. 즉시 차단하려면 별도의 블랙리스트가 필요하다.
- **HTTPS가 적용되지 않았다.** HTTP로만 통신하므로 실제 서비스에서는 토큰이 노출될 수 있다.
- **스키마 변경 시 데이터 초기화가 필요하다.** `create_all()`로 테이블을 만들고 있어 컬럼 추가 시 기존 테이블과 어긋난다.
- **단일 인스턴스다.** 이중화나 백업 체계가 없다.

### 14.2 향후 과제

| 우선순위 | 과제 |
|---|---|
| 상 | Alembic 마이그레이션 (데이터를 유지한 채 스키마 변경) |
| 상 | HTTPS 적용 및 클라우드 배포 |
| 중 | 리프레시 토큰 · 토큰 무효화 |
| 중 | DB 정기 백업 |
| 중 | 기간별 추세 통계 · 주간 리포트 |
| 하 | 목표 체중 · 혈압 관리 |
| 하 | 이상 수치 알림 |

## 부록. 용어 정리

| 용어 | 설명 |
|---|---|
| REST API | HTTP 메서드(GET/POST/PATCH/DELETE)로 자원을 다루는 API 설계 방식 |
| ORM | 파이썬 객체로 DB 테이블을 다루게 해주는 도구 |
| 마이그레이션 | 데이터를 유지한 채 테이블 구조를 변경하는 작업 |
| 볼륨 | 컨테이너 외부에 데이터를 보관하는 도커의 저장 공간 |
| 외래 키(FK) | 다른 테이블의 값을 참조하도록 강제하는 제약 조건 |
| CASCADE | 부모 데이터 삭제 시 자식 데이터도 함께 삭제하는 설정 |
| 해시 | 원문을 되돌릴 수 없게 바꾸는 단방향 변환. 비밀번호 저장에 사용 |
| salt | 같은 비밀번호라도 매번 다른 해시가 나오도록 섞는 무작위 값 |
| JWT | 사용자 정보와 만료 시각을 담아 서명한 토큰. 서버가 상태를 저장하지 않아도 됨 |
| Bearer 토큰 | `Authorization: Bearer <토큰>` 형태로 요청 헤더에 담아 보내는 인증 방식 |
